# QA_PREP — 서술형 대비

6문항 × 5분, AI·복사·붙여넣기 금지, 이전 답변 수정 불가. 질문은 내 제출물(코드, AI_COLLABORATION.md, HOW_TO_USE.md, git log)에서 생성된다고 보고 준비한다. 적은 문장은 사실이어야 하고 내가 설명할 수 있어야 한다.

## 답 골격 (4문장)
1. 무엇을 만들었나 / 무엇을 했나 (결론)
2. 왜 그렇게 했나 (근거, 버린 대안)
3. 어디서 깨질 수 있나 (구체적 약점과 파급)
4. 어떻게 확인했고, 무엇을 더 확인할 것인가 (명령·테스트·지표)

## 4유형과 재료
| 유형 | 묻는 것 | 재료 | 미리 해 둘 일 |
| --- | --- | --- | --- |
| 범위·검증 경로 | 구현과 의도적 제외·가정의 구분, 평가자가 확인할 경로 | HOW_TO_USE, verify.sh | 구현/제외/가정 표, 한 줄 검증 명령과 기대 출력 |
| 실패 경로 | 핵심 동작의 정상·재요청·제약 불충족·내부 실패, 기존 결과 처리 | FAILURE_MODES, 코드 상태 전이 | 4경로 + '기존 결과 보존' 원칙을 테스트로 고정 |
| 가정이 깨지는 조건 | 최적화·재사용이 기대는 가정, 깨지는 데이터, 추가 검증 | DECISIONS | 가정 / 깨지는 입력 / 감지 지표 / 되돌아가는 장치 |
| AI 협업 사실 | 사건 하나를 어떻게 파악·재현·수정했나, 받아들인 것·고친 것·버린 것 | AI_COLLABORATION, git log | 사건마다 증상→재현→제안→판단→확인을 그때그때 |

## 제출 확정 전 5분
- `$wrapup`이 만든 셀프 질문 6개를 소리 내어 답해 본다.
- 핵심 동작 하나의 흐름을 함수 이름까지 말할 수 있는지 확인.
- 사건 로그 한 건의 재현 명령과 확인 결과를 기억.
- 이 단계가 끝나면 AI와 메모 복붙을 일절 하지 않는다.

## 쓰는 요령
- 5분이면 4~6문장. 일반론 대신 내 코드의 이름·숫자·명령.
- 약점을 숨기지 않는다. '약점 → 파급 → 다음에 검증·개선할 것'이 좋은 답이었다.
- 모르는 것은 '확인하지 않았다'고 쓰고 확인 방법을 적는다.
