# 07 중간 점검 (verify)

## 언제
기능 동결 약 15분 전, 시작 후 130분쯤(21:10). 목표는 고치는 것이 아니라 **현재 상태를 정확히 아는 것**입니다. 이 점검으로 남은 시간의 작업 순서를 정합니다. 5~8분 안에 끝냅니다.

## 프롬프트

### 1. 요구 대 실행 결과

```
$verify 중간 점검이야. 기능 동결까지 <N>분 남았어. 고치지 말고 상태만 파악해줘.
- TASK.md 완료 조건 R번호별 상태: 통과 / 실패 / 미실행 (근거 한 줄)
- 동결 전에 끝낼 수 있는 것과 못 끝낼 것 (예상 시간)
- 못 끝낼 것은 '안 할 일'로 옮겼을 때의 영향
마지막에 남은 시간에 할 작업 순서를 제안해.
```

### 2. 로그인·권한이 있는 과제

```
$security-and-hardening 로그인·권한·입력 검증만 보자.
- 다른 역할이 URL이나 API를 직접 호출했을 때 막히는지
- 권한 검사가 화면이 아니라 처리 함수에 있는지
- 잘못된 입력이 저장되지 않는지
테스트나 명령으로 확인하고, 못 막는 곳은 고치지 말고 목록으로 보여줘.
```

### 3. 문서가 사실과 맞는지

```
git log와 실제 실행 결과를 기준으로 AI_COLLABORATION.md, HOW_TO_USE.md, DECISIONS.md에서 사실과 다른 문장이나 비어 있는 칸을 찾아줘. 고치지 말고 위치와 이유만 알려줘.
```

### 4. 화면 점검 (web 설치 시, 시간이 남을 때만)

```
$frontend-ui-engineering docs/SCREENS.md의 화면별 상태(비어 있음, 처리 중, 오류, 권한 없음)가 실제 화면에 구현됐는지만 점검해. 빠진 상태와 문구 불일치를 목록으로, 고치지는 마.
```

```
$fixing-accessibility <화면 파일>의 폼 라벨, 키보드 이동, 대비만 점검해. 최소 수정만 제안하고 적용은 내가 정한 뒤에.
```

## 정상이면
1. "통과"에 근거 명령이 있습니다. "미실행"을 통과로 세지 않습니다.
2. 실패와 미실행 R번호에 동결까지의 처리 순서가 붙어 있습니다.
3. 못 끝낼 것에 대한 결정을 제가 내릴 수 있게 영향이 적혀 있습니다.
4. 문서의 틀린 문장이 목록으로 나옵니다. 하나도 없다면 대조를 제대로 하지 않은 것일 수 있습니다.

## 아니면

검사 스크립트가 비어 있거나 0건일 때(verify.sh가 exit 2):

```
scripts/verify.sh의 검사 목록이 비어 있어. TASK.md 완료 조건 R번호마다 check 한 줄을 채워줘. 자동으로 확인할 수 없는 조건은 skip과 이유로 남겨. 채운 뒤 실행해서 결과를 그대로 보여줘.
```

결과를 믿기 어려울 때(별도 세션으로 교차 확인):

```
처음 보는 리뷰어로서 docs/TASK.md 완료 조건만 보고 현재 구현이 충족하는지 실행해서 확인해줘. 구현 코드를 먼저 읽지 말고 실행 결과로 판단해. 수정은 하지 마.
```
