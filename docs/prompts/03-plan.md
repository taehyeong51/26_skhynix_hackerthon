# 03 구성 선택과 계획 (plan)

## 언제
합의가 TASK.md에 기록된 직후, 약 10분(19:40~19:50). 코드는 아직 만들지 않습니다. 구성을 정하고, 슬라이스를 나누고, 확인 방법을 R번호에 붙입니다.

## 프롬프트

### 1. 구성 선택 (preflight 결과가 있을 때)

```
preflight 결과와 TASK.md를 보고 구현 구성을 두 가지 제안해.
조건: 이미 설치된 것과 표준 라이브러리만 쓰고 설치는 하지 마. 서버는 0.0.0.0. 과제가 요구한 실행 방식이 있으면 그것이 우선이야.
각각 한 줄 장단점, 예상 파일 수, 데이터 저장 방식을 쓰고, 마지막에 추천 하나와 이유를 알려줘. 파일은 만들지 마.
```

### 2. 계획

```
$plan 선택한 구성은 <구성>이고 기능 동결은 <HH:MM>이야. docs/ 아래에만 쓰고 코드는 만들지 마.
- 첫 슬라이스는 입력 → 핵심 규칙 → 출력이 한 번 도는 최소본이어야 해. 로그인·권한이 요구되면 가장 작은 형태를 여기에 포함해.
- 슬라이스마다 예상 시간(분)과 대응하는 R번호를 붙여. 합계가 동결까지 남은 시간을 넘으면 뒤에서부터 잘라낼 후보를 표시해.
- R번호마다 확인 방법(명령 또는 테스트 이름)을 정해. 정하지 못하면 비워 두고 표시해.
- 핵심 동작은 FAILURE_MODES.md를 채워. 중복·동시 요청, 제약 불충족, 내부 실패일 때 동작과 기존 결과 처리까지.

보고: 슬라이스 표 / 확인 방법이 비어 있는 R / 시간이 넘칠 때 자를 후보
```

### 3. 조정 (표를 읽은 뒤)

```
<슬라이스>는 '안 할 일'로 옮기고 DECISIONS에 이유를 한 줄 남겨. 나머지 순서는 그대로 두고 표만 다시 보여줘.
```

### 4. 과설계 점검 (core 설치 시)

```
$ponytail 지금 계획에서 요구에 없는 추상화·설정·옵션을 찾아서 빼고, 빼도 완료 조건이 그대로 충족되는지 R번호로 확인해줘.
```

## 정상이면
1. 첫 슬라이스가 80분 안에 끝날 크기입니다. 크다면 더 쪼갭니다.
2. 로그인·권한이 요구되는 과제면 첫 슬라이스에 들어 있습니다(10/31에는 로그인 문제가 후반에 드러났습니다).
3. 모든 R번호에 확인 방법이 있거나, 비어 있다는 표시가 있습니다.
4. 최적화·재사용이 계획에 있으면 "기대는 가정"이 DECISIONS에 같이 적혀 있습니다.
5. 슬라이스 합계가 동결 시각 안에 들어옵니다.

## 아니면

표가 너무 길거나 추상적일 때:

```
슬라이스를 20~30분 단위로 다시 쪼개줘. 각 슬라이스는 '무엇을 실행하면 무엇이 보이는지'를 한 줄로 쓸 수 있어야 해. 쓸 수 없으면 아직 모호한 거니까 나에게 물어.
```

확인 방법을 정하지 못한 R이 있을 때:

```
확인 방법이 비어 있는 R번호마다 '사람이 화면에서 확인' / '명령으로 확인' / '확인 불가' 중 어느 쪽이 가능한지와 가장 싼 방법을 제안해.
```
