# 08 기능 동결 (freeze)

## 언제
기능 동결 시각(약 144분, 21:24). 이후에는 새 기능을 만들지 않습니다. 남은 시간은 실패 수정, 문서, 제출 준비에 씁니다. 동결 뒤에 "하나만 더" 넣는 것이 제출 직전 사고의 가장 흔한 원인입니다.

## 프롬프트

### 1. 동결 선언과 전체 확인

```
지금부터 기능 동결이야. 새 기능은 만들지 마.
1. 현재 커밋에 freeze 태그를 붙여. 커밋되지 않은 변경이 있으면 먼저 보여줘.
2. $verify 로 전체를 한 번 실행해.
3. 실패나 미실행 항목마다 '지금 고친다 / 알려진 한계로 적는다' 중 어느 쪽이 맞는지, 걸리는 시간과 위험을 한 줄로 제안해. 결정은 내가 해.
```

### 2. 결정 전달

```
<항목>은 고친다, <항목>은 알려진 한계로 적는다.
고치는 건 최소 수정으로 하고, 같은 확인 명령이 통과해야 커밋해. 고친 뒤에는 $verify 전체를 다시 실행해서 다른 항목이 깨지지 않았는지 보여줘.
한계는 HOW_TO_USE.md '알려진 한계'에 사실대로 적어(원인을 확인하지 못했으면 '원인 미확인'이라고).
```

### 3. 정리 후보 찾기 (지우기 전에 목록만)

```
제출물에서 정리할 것을 찾아줘: 디버그 출력, 임시 파일, 주석 처리된 코드, 쓰지 않는 의존성, 비밀값, 키트 원본이 섞인 파일. 목록과 위치만 보여주고 지우지는 마.
```

## 정상이면
1. `git tag`에 freeze가 있고, 그 이후 커밋은 수정 또는 문서뿐입니다.
2. 수정마다 확인 명령 통과 기록과 함께 `$verify` 전체 재실행이 있습니다.
3. 고치지 않기로 한 것이 '알려진 한계'에 구체적으로 적혔습니다.

## 아니면

동결 뒤에 AI가 기능을 추가하려 할 때:

```
동결 이후야. 방금 변경은 새 기능이니 되돌릴지 내가 정할게. 변경 내용을 요약하고, 지금 제출 가능한 상태가 깨졌는지만 확인해줘.
```

수정이 다른 곳을 깨뜨렸을 때는 새로 고치기 전에 되돌립니다.

```
방금 수정이 <항목>을 깨뜨렸어. 그 커밋을 git revert로 되돌리고, 되돌린 상태에서 $verify 전체가 동결 시점과 같은지 보여줘. 그다음에 다른 접근을 제안해.
```
