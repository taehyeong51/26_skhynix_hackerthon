# ux

업무 화면의 성공은 "사용자가 할 일을 빠르고 틀리지 않게 끝내는 것"이다. 화려함보다 훑어보기 쉬움, 일관성, 익숙한 패턴, 정확한 문구가 먼저다. 4시간 과제이므로 화면 수와 장식을 최소로 한다.

입력: 사용자가 말한 단계(기획 / 구성·설계 / 검증). 없으면 docs/SCREENS.md가 얼마나 채워졌는지 보고 다음 단계를 고른다.

## A. 기획 (인터뷰 직후, 5분)
1. TASK.md의 사용자·역할마다 사용 장면을 한 줄로 쓴다: 누가 / 어디서(PC·휴대폰) / 무엇을 끝내려고 / 얼마나 자주.
2. 장면마다 "가장 먼저 봐야 하는 것" 하나를 정한다. 모르면 담당자 질문 문구를 만든다(사용자가 보낸다).
3. 화면 조건을 완료 조건 R번호로 TASK.md에 추가한다. 확인 가능한 문장으로만 쓴다(예: "직원은 첫 화면에서 오늘 빈 회의실을 본다").

## B. 구성 (계획 단계)
1. 화면 목록: 역할 매트릭스에서 출발한다. 화면마다 목적 한 줄, 대응 R번호, 볼 수 있는 역할. R번호가 없는 화면은 만들지 않는다.
2. 이동 흐름: 역할별로 `로그인 → … → 완료`를 한 줄로. 핵심 과업이 세 번 이하의 이동으로 끝나야 한다.
3. 첫 E2E 슬라이스에 들어갈 화면(로그인 + 핵심 화면 하나)을 표시한다.

## C. 설계 (계획 단계, 화면마다)
1. 상태: 정상 / 비어 있음 / 처리 중 / 오류 / 권한 없음. 상태마다 화면에 보이는 것을 한 줄로. FAILURE_MODES.md의 '사용자에게 보이는 것' 칸과 맞춘다.
2. 문구: 버튼은 동사로("예약하기", "배정안 적용"). 오류는 무엇이 왜 안 됐고 어떻게 하면 되는지("이미 예약된 시간입니다. 다른 시간을 고르세요"). 파괴적 동작은 확인을 받고 결과를 보여 준다.
3. 입력: 필수 표시, 형식 힌트, 검증은 서버에서 하고 화면은 같은 메시지를 보여 준다. 실패해도 입력값은 남긴다.
4. 배치: 목록은 훑어볼 열만, 숫자는 오른쪽 정렬, 핵심 동작 버튼은 한 화면에 하나만 강조. 프레임워크나 CSS 라이브러리는 이미 설치된 것만 쓴다.
5. 결정은 docs/DECISIONS.md에 한 줄(예: "목록 대신 주간 표 — 총무는 겹침을 한눈에 봐야 함").

## D. 검증 (첫 E2E 직후, 동결 전)
1. 사람 확인 목록을 SCREENS.md의 화면·상태에서 뽑아 사용자에게 준다. 화면마다 정상 1개 + 실패 상태 1개 이상.
2. 자동화 가능한 것은 `$e2e` 단계로 옮긴다(상태 문구와 개수로 판정).
3. 접근성 최소선: 모든 입력에 라벨, 키보드로 핵심 과업 완료, 포커스가 보임, 글자 대비. vendor 스킬 `fixing-accessibility`가 있으면 그 기준을 쓴다.
4. 결과는 SCREENS.md '확인' 칸과 AI_COLLABORATION.md(사람이 발견한 문제는 '발견: 사용자')에 남긴다.

## 하지 않을 것
- 요구에 없는 화면, 애니메이션, 테마, 대시보드 장식
- 패키지 설치(아이콘·UI 라이브러리 포함)
- 화면에서 버튼만 숨기고 권한 검사를 생략하는 것(권한은 처리 함수에서)

더 깊은 구현 요령(컴포넌트 구조, 빈·오류 상태, 반응형)은 vendor 스킬 `frontend-ui-engineering`, 시각 방향은 `frontend-design`을 참고한다(설치했을 때).
